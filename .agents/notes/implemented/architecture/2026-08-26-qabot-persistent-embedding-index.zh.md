# Agent Note: 按内容与模型标识持久化 Qabot 向量

Status: implemented

[English](2026-08-26-qabot-persistent-embedding-index.md) | 中文

## Problem

Qabot 在 SQLite 中保存知识分块，并生成向量用于语义检索。进程启动时重建向量表会丢弃仍然有效的向量，延迟服务就绪，并在文档和模型都未变化时重复产生供应商调用及费用。

文本向量和视觉向量的请求格式与检索语义也不同。将两者作为可互换向量存储，会让维度或模型不兼容的向量进入同一次余弦检索。

## Decision

`embeddings` 表持久保存在 `kb.db` 中。每条文本向量记录文档 ID、序列化向量、SHA-256 内容哈希、embedding 模型标识和 `vector_kind = 'text'`。只有内容哈希及模型标识都与当前文档和配置一致时，`embedMissing()` 才复用现有记录。远程模型变化会使全部文本向量失效；远程模型下的内容变化只使受影响的分块失效。

本地字符 TF-IDF 模型的模型标识包含确定性的语料指纹，因为 IDF 权重依赖所有已索引分块。因此，本地语料发生任何变化时会更新全部本地向量。旧版表中的记录没有可信的模型和内容元数据，系统会重新计算一次，而不会在缺少依据时将其标记为当前模型生成。

文本检索只选择 `vector_kind = 'text'`。视觉索引将下载的飞书图片持久化到 `vision_assets`，在同一文档 ID 下保存 `vector_kind = 'vision'` 的向量，并按配置使用 `qwen3-vl-embedding` 调用 DashScope 多模态接口。员工文本查询由同一个视觉模型生成向量，只与当前视觉记录比较，再把结果并入文本检索。`(doc_id, vector_kind)` 主键允许两种表示共存而不混用维度。

只有员工问题明确要求图片、图表、截图、照片、示意图或类似视觉材料时，系统才执行视觉检索。视觉查询向量持久化在 `vision_query_cache` 中，以视觉模型标识和规范化员工问题的 SHA-256 哈希为键。同一个问题的重复检索、会话轮询和回答图片选择都会复用该向量。视觉结果随助手消息返回时，`conversation_media` 记录会话 ID、助手事件序号、文档 ID 和排序。会话历史能够恢复同一组图片且不再次调用模型；图片字节继续保存在 `vision_assets` 中，并通过需要登录的门户代理返回。

## Alternatives considered

- **每次启动重建全部向量：** 不采用，因为未变化内容会产生相同的供应商工作，并让可用性依赖全量重建。
- **只记录文档哈希：** 不采用，因为 `EMBED_MODEL` 变化后，旧模型或旧维度的向量仍会被错误复用。
- **用当前模型名称回填旧记录：** 不采用，因为无法确定存量向量由哪个模型生成，重新标记会静默混用模型。
- **文本和图片使用同一种向量类型：** 不采用，因为多模态 API、向量维度和排序行为不同于当前文本 `/embeddings` 请求。

## Consequences

文档和模型未变化时，重复启动不会调用 embedding。远程模型下的文档更新只重新计算变化分块，模型变化则执行一次明确的全量更新。本地 TF-IDF 在语料变化后全量更新，以保证权重正确。现有数据库会对旧记录执行一次更新。配置视觉索引后，系统下载飞书文档图片、保留图片字节以支持模型切换、清理源文档中已删除的图片，并支持文本到图片的跨模态检索，而不会让视觉向量进入文本余弦检索。相同的文本搜图问题会复用持久化查询向量，已返回的图片通过消息关联在刷新后保留。视觉录入需要飞书媒体下载权限和 DashScope API Key；未配置 `VISION_EMBED_MODEL` 时保持关闭。
