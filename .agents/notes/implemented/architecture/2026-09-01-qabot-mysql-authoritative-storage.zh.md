# Agent Note: 将 MySQL 设为 Qabot 生产数据权威源

Status: implemented

[English](2026-09-01-qabot-mysql-authoritative-storage.md) | 中文

## Problem

Qabot 的生产状态分散在 MySQL 投影、本地 SQLite 数据库和 DSH JSONL 文件中。因此，即使 `hr_system` 正常，从不同主机启动或重启进程仍可能看到不同的服务人员配置、知识检索结果或模型历史。

## Decision

当 `QABOT_DATABASE_BACKEND=mysql` 时，Qabot 使用 MySQL `hr_system` 作为生产数据权威源。会话、投影消息、工单、审计记录、Outbox、服务人员配置、知识文档与向量、知识提交记录、查询向量缓存和 DSH 模型原始会话事件统一存入完成迁移的 MySQL 数据库。SQLite 继续作为明确选择的开发和测试实现。

模型知识检索直接读取 MySQL 中已发布且处于生效期内的版本。系统先执行关键词匹配，再进行语义排序，并按规范化问题哈希与向量模型标识缓存查询向量。重复的相同问题复用已存向量；普通文本问题不会调用视觉向量服务。

DSH 会话持久化在同一事务中追加会话头和连续事件到 `dsh_model_sessions` 与 `dsh_model_session_events`。恢复会话根据 MySQL 元数据发现记录，不依赖文件路径。一次性迁移器把可读取的旧 JSONL 会话和服务人员记录复制到 MySQL，并在 `qabot_data_imports` 记录完成状态；源文件保留为回退证据，后续在 MySQL 删除的数据不会被再次导入。

知识管理仍使用本地录入索引进行解析、审核和缺失向量计算。每次变更都会把完整的已审核状态、向量、资产、版本元数据和提交队列投影到 MySQL，之后生产检索才能使用。本地索引是可重建的录入来源，不是生产读取权威源。

## Alternatives considered

- **继续把 MySQL 仅作为报表投影：** 拒绝，因为生产回答和派单仍会依赖主机本地文件。
- **只保存渲染后的聊天消息：** 拒绝，因为助手恢复需要完整的 DSH 类型化事件日志，包括工具调用和回合标记。
- **每次请求都重新计算查询向量：** 拒绝，因为重复问题会消耗向量额度，却不会改善检索质量。
- **导入后删除旧文件：** 拒绝，因为在验证 MySQL 切换期间保留文件可以提供非破坏性的回退证据。
- **让所有开发测试都依赖 MySQL：** 拒绝，因为快速隔离的 SQLite 测试仍有价值，而且生产模式缺少明确 MySQL URL 时已经会直接失败。

## Consequences

生产环境重启或更换主机后，可以从同一数据库结构恢复服务团队、可检索知识和模型历史。迁移 11 新建服务人员、模型会话、迁移标记、查询缓存和知识提交表，业务时间统一使用 Asia/Shanghai `DATETIME(3)`。生产启动和问答依赖 MySQL 可用。新审核知识必须完成投影后才参与检索；录入或同步失败时，MySQL 中既有的已发布版本仍可使用。

MySQL 集成测试必须显式配置 `QABOT_TEST_MYSQL_URL`，使用唯一记录标识并在结束后清理。真实验收必须证明知识回答成功、模型原始事件已经持久化，并且 Qabot 重启后无需读取旧会话文件即可恢复。
