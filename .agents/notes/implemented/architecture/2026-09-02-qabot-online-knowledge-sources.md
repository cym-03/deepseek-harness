# Agent Note: Manage Qabot knowledge as synchronized online sources

Status: implemented

English | [中文](2026-09-02-qabot-online-knowledge-sources.zh.md)

## Problem

Qabot exposed document submissions, review, version comparison, publication windows, offline state, and deletion as separate operator actions. That workflow did not match continuously edited Feishu documents and kept production source configuration in a host-local JSON file.

## Decision

MySQL `knowledge_sources` is the authoritative source registry. Each record stores a title, immutable Feishu URL, maintenance group, submitter identity, synchronization status, last successful synchronization time, last error, and optional removal time. Existing sources migrate to the `other` group with `system-migration` as their submitter.

The maintenance groups are `hr`, `admin`, `it`, `finance`, and `other`. All active sources remain available to every employee question. A service-desk operator may maintain sources in the operator's group, while SystemAdmin may maintain every source. The signed portal identity supplies the submitter employee ID and display name. Synchronization uses that submitter's Feishu user authorization and never falls back to a bot, supervisor, or another employee.

Adding a source starts its first synchronization. Its text, ordinary images, and embedded boards become searchable only after that synchronization succeeds. Each board uses its stable block token as an independent visual asset and its nearest heading as retrieval context, while every derived document and asset remains owned by the submitted source according to [Keep derived knowledge documents under their submitted online source](../bug-fix/2026-09-04-derived-knowledge-documents-belong-to-online-source.md). Every synchronization exports its current snapshot. The configured OCR model extracts a new or changed board's visible text into the board's searchable chunks; an unchanged asset hash reuses both that text and the visual vector without another model request. A changed snapshot replaces the current asset and calculates new OCR text and one new vector. Dense OCR output is divided into overlapping regions only after the whole snapshot reaches the configured output limit. Blank regions contribute no text, and the smallest region retains complete text fields from an otherwise incomplete structured response. A five-minute scheduler and explicit row action perform later incremental synchronization. Unchanged document content reuses existing vectors. Changed content creates an internal version, archives every previously published version in the same projection transaction, and atomically replaces the current searchable content. Retrieval independently selects only the greatest published version number for each document, so inconsistent historical status cannot mix old and current content. Internal versions support safe replacement and vector reuse but are not shown to operators.

A failed first synchronization keeps the source record unavailable for retrieval. A failed later synchronization keeps the last successful content searchable and records the error on the source. Soft removal stops scheduling and immediately excludes the source's documents, text vectors, visual vectors, and images from retrieval. Re-adding the same normalized URL restores the existing record and can reuse unchanged indexed data.

The portal presents a compact source table with title search, a maintenance-group filter, health totals, per-source synchronization state, last synchronization time, and row actions for editing, synchronizing, and removing. The source title opens the original document. It no longer calls or displays review, version-difference, publish, reject, effective-window, offline, or separate delete workflows. Source mutations and synchronization outcomes remain in the existing audit stream.

Direct Docx, Feishu Sheets, and Bitable links are accepted, and Wiki sources may resolve to the same types. Sheets are read with the submitter token in bounded cell ranges and stored as searchable records that preserve worksheet, header, and row field names. A direct Sheets link that identifies one worksheet indexes only that worksheet.

## Alternatives considered

- **Keep approval and publication steps:** rejected because these curated documents are intended for all employees and operational owners need synchronized live content rather than release management.
- **Use Feishu event callbacks immediately:** rejected for this phase because five-minute polling plus manual synchronization meets the freshness requirement without another externally configured integration.
- **Hard-delete a removed source:** rejected because soft removal preserves auditability and lets an unchanged source reuse indexed data when restored.
- **Introduce Milvus:** rejected because the current data size and MySQL vector persistence do not justify another production dependency.
- **Grant a bot access to every document:** rejected because source access belongs to the employee who submitted it and per-document bot grants do not scale with the document set.

## Consequences

Operators manage one durable source record instead of a submission and publication workflow. MySQL availability is required to list, authorize, synchronize, or remove production sources. The local ingestion database remains a rebuildable working index and cannot activate a source by itself.

Source changes can take up to five minutes to appear without a manual synchronization; the deployment launcher preserves that five-minute interval instead of overriding it. The portal requests document, media, board, and offline-refresh OAuth scopes, encrypts each submitter's renewable credential in MySQL, refreshes it when needed, and gives Qabot only a short-lived access token through an authenticated internal endpoint. Embedded images require `docs:document.media:download`, embedded boards require `board:whiteboard:node:read`, and the submitter must retain access to the source. Ordinary image requests carry the parent Docx context and fall back to Feishu's source-file preview stream and temporary URL; boards use the board-image export endpoint. Original media remains stored for display, SVG boards normalize to PNG, and only assets exceeding the model request limit receive a resized compressed copy for OCR and embedding. MySQL projection updates unchanged visual assets under stable IDs so durable conversation references remain valid. OCR output is split into ordinary knowledge chunks. A whole-image or outer-region response terminated by the configured output limit is divided further instead of indexed; only a smallest region may retain its already complete text fields when the provider omits the final structured-response delimiter. Visual retrieval returns either a strong match or a lower-scoring cluster of corroborating images and rejects a lone weak result. Matching visual assets render as cards after the answer, while board OCR text reaches the answer model through ordinary knowledge retrieval. Missing or expired authorization leaves the last successful content searchable and records a source error; an unavailable visual asset invokes neither OCR nor the visual embedding model. A SystemAdmin can claim an active `system-migration` source by submitting its link again or starting that source's explicit synchronization; ordinary active duplicates remain rejected. The retained internal versions and historical review tables are implementation history and are not operator-facing product concepts.
