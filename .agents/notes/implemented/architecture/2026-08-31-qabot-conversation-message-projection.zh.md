# Agent Note：将 Qabot 会话消息投影到 MySQL

状态：已实现

[English](2026-08-31-qabot-conversation-message-projection.md) | 中文

## 问题

Qabot 将会话元数据保存在业务数据库中，但员工和智能助手消息只能通过本地 DSH 会话文件读取。因此，当服务从不同目录启动或暂时无法发现对应会话文件时，门户仍能列出会话，却会显示空白聊天记录。工单回复已经持久化，但读取时将其与模型消息合并仍然依赖本地文件。

## 决策

DSH 会话事件继续作为模型可见历史的权威记录。Qabot 同时在配置的 MySQL 业务数据库中维护幂等的 `conversation_messages` 投影。每条投影记录由会话、来源类型和来源标识唯一确定，并保存来源顺序、角色、正文、媒体引用和创建时间。读取会话时先吸收当前可用的 DSH 事件与工单回复，再按时间顺序返回数据库投影。DSH 某次读取为空或暂时不可用时，不删除已经投影的消息。

MySQL 还按“角色范围内的员工和会话”保存单调前进的已读位置。员工会话列表统计员工已读位置之后的智能助手、人工客服和系统消息；客服工单列表统计客服已读位置之后的员工消息。打开有权访问的会话后，该阅读者的已读位置只推进到响应实际包含的最大消息 ID，因此并发到达的后续消息仍保持未读。迁移会将已有消息的最大 ID 记为功能启用基线，历史记录不会一次性变成未读积压，后续新增消息仍可正常计数。

`project-messages` 命令回填所有已知会话，且不会调用语言模型、文本向量模型或视觉向量模型。正常读取会话也会持续更新投影。MySQL 是当前生产实现；SQLite 和 PostgreSQL 在具备等价消息 Repository 前，继续使用原有的读取时合并逻辑。

## 考虑过的替代方案

- **继续仅用本地会话文件提供员工聊天记录：** 不采用，因为业务界面的可用性仍会依赖进程启动路径和本地文件发现。
- **用业务消息表替代 DSH 事件：** 不采用，因为所有模型可见输入必须能够从 DSH 会话日志重建。
- **复制消息但不保存稳定来源标识：** 不采用，因为重试和重复读取会产生重复聊天记录。
- **将已读位置只保存在浏览器：** 不采用，因为首次初始化、切换浏览器和清理本地存储都无法维持一致的未读状态。

## 结果

即使后续某次 DSH 读取为空，员工端和服务台仍能从 MySQL 恢复完整聊天历史。未读角标可以跨刷新和浏览器保留，打开一个会话只会清除当前阅读者的已读位置。现有模型记忆语义保持不变。时间线读取会增加小型的投影与已读位置数据库事务，MySQL 部署必须在提供服务前执行 `008_conversation_messages.sql` 和 `009_conversation_message_reads.sql`。来源键具有唯一约束，因此历史回填命令可以安全重复执行。
