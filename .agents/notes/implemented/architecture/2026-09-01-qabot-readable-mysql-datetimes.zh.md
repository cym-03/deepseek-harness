# Agent Note: 使用可读格式保存 Qabot MySQL 日期

Status: implemented

[English](2026-09-01-qabot-readable-mysql-datetimes.md) | 中文

## Problem

Qabot 使用 Unix 毫秒整数在 MySQL 中保存业务日期。直接检查数据库时，运维人员必须先手工转换，才能判断会话、消息、工单、知识版本、审核或集成任务发生变更的时间。

## Decision

Qabot 的 MySQL 业务日期统一使用 Asia/Shanghai 时区的 `DATETIME(3)` 字段。数据库直接显示 `年-月-日 时:分:秒.毫秒`，字段备注说明对应的业务事件，不再把值描述为 Unix 时间戳。标识、计数、来源顺序、乐观版本和未读消息位置仍然使用整数。

Repository 接口与 HTTP 响应继续使用 Unix 毫秒。MySQL 适配层写入 JavaScript `Date` 参数，并把读取到的日期转换为毫秒，因此超时计算、时间排序和门户响应字段保持既有语义。MySQL 连接使用 `+08:00` 时区，迁移 10 在同一时区转换已有毫秒值并保留毫秒精度。

## Alternatives considered

- **保留整数时间戳并提供格式化查询视图：** 拒绝，因为日常查表和下游报表仍会遇到不可读的源字段。
- **保存格式化文本：** 拒绝，因为文本允许无效日期，而且无法可靠使用原生日期比较、运算和索引。
- **同时保留整数和日期字段：** 拒绝，因为两份时间表示可能产生偏差，并要求每个写入方同时更新两列。
- **把所有应用接口改为日期字符串：** 拒绝，因为改善存储可读性不需要改变超时运算和现有门户 API。

## Consequences

运维人员无需转换即可读取 MySQL 日期，同时仍可使用原生日期条件。适配层是可读数据库值与应用毫秒值之间的唯一转换位置。工单统计使用 `TIMESTAMPDIFF`，不再直接对日期做数值相减。部署必须先执行迁移 10，再让写入 `Date` 参数的代码对外服务；后续 MySQL 业务时间字段统一使用相同时区的 `DATETIME(3)`。
