# Agent Note: 通过 Outbox 投递 Qabot 通知

Status: implemented

[English](2026-08-27-qabot-integration-outbox.md) | 中文

## Problem

工单 HTTP 操作会同步调用飞书。飞书临时失败可能把已经完成的工单修改报告为失败，促使调用方重复操作；进程重启也会丢失尚未完成的通知。

## Decision

Qabot 在返回业务结果前，将转人工通知和客服公开回复持久化到 `outbox.db`。每条消息包含唯一幂等键、JSON 载荷、尝试次数、下次可用时间、最后错误和终态。重复写入同一业务事件不会产生新记录。满意度保留在员工门户会话中，不使用外部通知事件。

单进程后台任务轮询待处理消息。已配置的处理器完成成功投递；失败会记录有长度限制的错误，并按最大六十秒的指数退避安排重试。连续失败八次后消息进入 `failed`。没有对应集成处理器时消息保持待处理，因此补充飞书配置不会丢弃消息。

转人工载荷包含读取时的工单版本。工单已经进入其他版本或不再等待客服时，后台任务会直接完成过期通知而不发送，避免转派前的延迟事件通知旧队列。部署只运行一个 Qabot 执行进程，后台任务会拒绝该进程内重叠执行的轮询。

## Alternatives considered

- **同步发送并返回供应商错误：** 拒绝，因为工单持久化与外部投递不共享事务，响应无法真实回滚工单。
- **只在内存重试：** 拒绝，因为进程重启会丢失排队任务和重试历史。
- **使用工单行充当通知队列：** 拒绝，因为一张工单会产生独立重试的转人工和回复事件。
- **立即引入消息代理：** 暂缓，因为首发单公司部署只有一个 Qabot 进程；SQLite Outbox 无需增加运维服务即可提供持久语义。迁移 PostgreSQL 时可以保留相同 Repository 行为。

## Consequences

飞书故障不会阻塞工单操作，待处理任务可跨重启保留，重复入队不会产生重复记录。当供应商发送成功但进程在记录完成前停止时，投递属于至少一次；如果飞书提供合适的幂等键，还需要在供应商侧接入。失败消息保留在数据库中供查询。单进程后台任务不是多实例抢占协议，在多个 Qabot 工作进程消费同一数据库前必须改成行级领取。
