# Agent Note: Qabot 工单优先级与 SLA 策略

Status: implemented

[English](2026-08-31-qabot-ticket-sla-policy.md) | 中文

## Problem

人工服务工单没有优先级和响应截止时间，队列无法区分紧急事项、识别服务超时，也无法说明某次策略修改是否影响了工单。如果只在门户硬编码时限，浏览器状态会成为真源，通过 API 创建的工单也不会受到管理。

## Decision

MySQL 为每个服务组保存一条可启用的策略，包括默认优先级、首次响应时长和解决时长。员工完成转人工或客服完成转接时，系统把所选服务组策略应用到工单，并保存绝对毫秒时间戳。首次公开人工回复写入 `first_agent_response_at`，后续回复不会覆盖该时间。

工单优先级与 SLA 时间是业务投影字段，随现有工单资源返回。有权访问工单的客服可以携带当前版本修改单张工单优先级。SystemAdmin 可以查询和更新服务组策略。两类操作都在数据库修改成功后追加审计记录。

门户主管配置页用于编辑策略并展示最近的审计记录。工单工作区展示优先级和当前生效的截止时间：首次公开人工回复前显示首次响应时限，回复后显示解决时限。时长按自然经过分钟计算，工作时间和节假日不会暂停计时。

## Alternatives considered

**只在浏览器计算截止时间。** 否决，因为不同客户端可能得到不同结果，后台 SLA 检查没有持久化依据，通过 API 创建的工单也没有截止时间。

**所有服务组共用一条策略。** 否决，因为 IT、人事、行政、财务和综合服务需要独立调整目标。

**策略修改时重算全部未结束工单。** 否决，因为这会静默改变已经建立的服务承诺。策略在工单进入服务组时生效；显式转接会应用目标服务组的当前策略。

**首版实现工作时间日历。** 推迟，因为日历归属、地区节假日和各服务组班次需要独立配置。自然分钟的含义明确且可测试。

## Consequences

服务台可以根据持久化数据识别优先事项和超时工单。策略与优先级修改可通过审计日志追溯，乐观版本避免并发修改互相覆盖。转接会为接收服务组重置两类截止时间和首次响应标记。现有 SQLite 与 PostgreSQL 开发后端会返回中性优先级字段，但不持久化可配置策略；生产策略管理因此要求使用 MySQL 后端。
