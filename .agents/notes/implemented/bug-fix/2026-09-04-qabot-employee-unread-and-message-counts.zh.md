# Agent Note: 前台未读状态和消息条数使用员工可见时间线

Status: implemented

[English](2026-09-04-qabot-employee-unread-and-message-counts.md) | 中文

## Problem

员工会话列表统计 DSH 原始用户和助手事件。重试事件以及只为智能助手上下文注入的消息会让该数值与持久化会话时间线返回的气泡数量不同。客服回复还会在写入 `conversation_messages` 之前发布实时变更，因此员工收到事件并刷新列表时看不到未读消息。发送消息和后台刷新随后又会自动推进员工阅读位置，浏览器还会隐藏当前会话的未读标记。

## Decision

会话列表响应从 `conversation_messages` 读取各会话条数，与会话详情使用同一份 MySQL 时间线。客服回复接口在发布实时工单变更之前完成消息投影。发送消息和后台刷新不再推进员工阅读位置。只有会话详情请求明确携带 `markRead=1` 时才推进阅读位置，且只推进到该次响应所包含的最大消息 ID。浏览器在明确已读请求完成前，对当前会话和其他会话都显示未读标记。

人工接管期间的员工消息继续保留在 DSH 会话中供智能助手理解上下文，但不再从 DSH 事件投影，因为对应工单回复才是员工界面的持久化副本。

## Alternatives considered

- **继续使用 DSH 事件数：** 拒绝，因为内部重试和注入上下文不是员工可见消息。
- **在浏览器中计算未读：** 拒绝，因为换浏览器或刷新页面会丢失阅读位置。
- **将当前会话视为自动已读：** 拒绝，因为新回复到达时员工未必正在查看最新消息。
- **先发布实时事件再投影：** 拒绝，因为第一次列表刷新仍可能早于新回复入库。

## Consequences

侧栏条数与员工打开会话后实际渲染的消息数量一致。每条新的 AI 或人工回复都会产生持久化未读标记，当前会话也不例外。明确进入该会话后标记才会清除，同时不会把响应之后到达的消息提前标记为已读。刷新页面会打开选中的会话，因此初次详情请求返回的消息会被标记为已读。
